# GAP-006 阶段 0：Epic 与 User Stories

## 1. Epic

**EPIC-006：商机产品与跟进链路差异补齐**

作为销售人员，我希望在现有 CRM 商机模块中完成阶段流转、输单记录、产品报价、金额计算和跟进联动，以便从商机建立到持续跟进的关键数据保持一致，同时不重复建设现有领域模型。

依赖：客户、产品、组织权限、数据权限、业务字典和通用跟进能力。

## 2. User Story 清单

### US-006-01 商机阶段流转

作为销售人员，我希望商机按照所属阶段组向后流转，以便准确反映当前销售进度。

阶段 0 验收口径：

- 复用现有状态组和状态模型。
- 阶段必须属于商机当前状态组。
- 默认禁止回退；是否允许跳级或管理员回退在阶段 1 冻结。
- 赢单率范围、排序和终态后的重新打开规则必须补充设计。

### US-006-02 输单原因

作为销售人员，我希望将商机标记为输单时记录原因，以便后续复盘。

阶段 0 验收口径：

- 复用现有 `endStatus/endRemark`。
- 输单时原因必填。
- 赢单与输单状态不能同时提交。
- 自由文本或字典选项由需求负责人进一步确认。

### US-006-03 产品报价与金额

作为销售人员，我希望选择已有产品，录入商机价格和数量并自动计算折扣及总价，以便形成可核验的商机报价。

阶段 0 验收口径：

- 复用现有商机产品行、产品主数据和金额字段。
- 行金额、产品合计、折扣和整单金额由服务端校验和计算。
- 价格、数量和折扣必须有边界校验。
- 未确认报价单号、版本、审批、有效期前，不建立 `Quote`/`Quotation` 模型。

### US-006-04 产品关联约束

作为业务管理员，我希望产品停用、删除和重复选择有明确规则，以便历史商机数据保持可追溯。

阶段 0 验收口径：

- 产品必须来自现有 `crm_product`。
- 同一商机是否允许同一产品多行，需要业务确认。
- 产品被商机引用后的删除、停用或快照策略必须进入阶段 1。
- 不得在 PKG-02 内复制产品主数据。

### US-006-05 商机跟进联动

作为销售人员，我希望新增跟进记录时关联商机，并同步最近跟进状态和下次联系时间，以便在商机详情中查看完整跟进轨迹。

阶段 0 验收口径：

- 复用通用跟进记录和 `bizType/bizId` 机制。
- 插入跟进和更新关联业务数据应具备一致事务边界。
- 业务类型、业务 ID、联系人和商机 ID 必须校验合法性。
- 是否允许编辑跟进记录由原型或验收标准确认。

### US-006-06 禁止重复建模

作为技术负责人，我希望 GAP-006 复用现有商机领域对象，以便避免平行实体、重复表和两套接口长期不一致。

阶段 0 验收口径：

- 新需求首先映射到现有 DO、表、Service、Controller、API 和页面。
- 仅页面入口缺失或命名不同，不能作为新建模型依据。
- 新表或新子能力必须提供原型证据、现有模型无法表达的说明和 AISDD 设计。
- 数据库变化只能以 `database/new` 增量脚本提交。

## 4. 非本阶段承诺

- 本文件不表示上述改进已经编码完成。
- 本阶段不承诺独立报价单、审批、版本或有效期能力。
- 未运行的浏览器、接口和数据库验证不视为通过。
- User Story 的最终字段、交互和异常提示在阶段 1 AISDD 设计后冻结。
